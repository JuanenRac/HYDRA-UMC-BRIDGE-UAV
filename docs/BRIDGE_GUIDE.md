# HYDRA-UMC-BRIDGE-UAV Technical Guide

## Scope and operating model

This bridge maps a validated `BridgeJob` to a **static high-level flight-request plan**, and separately tracks a real link-loss heartbeat. `UavCoordinator` has no MAVLink or vendor SDK dependency, so it can be verified on Windows, Linux or CI without a real UAV. It emits only a named flight request - `ARM`, `TAKEOFF`, `GOTO_WAYPOINT`, `HOVER_AND_CAPTURE` or `RETURN_TO_LAUNCH`, plus the standalone `LAND` and `DISARM` - never a real attitude/throttle command.

**Honesty fix:** this request used to be named `PRE_FLIGHT_CHECK`. The real MAVLink command it sends (`MAV_CMD_COMPONENT_ARM_DISARM`, arm) genuinely arms the vehicle - PX4/ArduPilot run their own pre-arm check suite as part of processing an arm request, so there is no separate, real, standard MAVLink command that runs those checks without arming. Naming it "check" made a real arm command sound like an inert, read-only query. Renamed to `ARM`, and `mavlink_transport.py`'s own `send()` now requires an explicit `confirm_arm=True` before actually sending it - a real arm command needs its own deliberate opt-in, not just the same shared cell/machine gate every other request already passes through.

`PREPARE`/`LOAD`/`PROCESS`/`UNLOAD`/`COMPLETE` map to their own request; `ABORT` and `COMPLETE` both resolve to `RETURN_TO_LAUNCH` - a normal mission end and an emergency abort both mean "come home", the real standard UAV failsafe action. A request that brings the vehicle to a safe state (`RETURN_TO_LAUNCH`, `LAND`, `DISARM`; `UavCoordinator.SAFE_STATE_REQUESTS`) is accepted whatever the cell and the machine say, so a `COMPLETE` while the vehicle is flying (not `IDLE`) or the cell is inhibited still brings it home; the productive phases (`ARM` to `HOVER_AND_CAPTURE`) stay behind the shared gate, which means they are refused while the autopilot reports the vehicle as anything but `IDLE`. How a continuing flight is to be expressed to that gate is an open question. An unknown SDK phase is rejected. `UavCoordinator.dispatch()` itself is still `plan-only`, never a live flight command - only `mavlink_transport.py`'s `MavlinkFlightControl`, given that already-gated dispatch explicitly, ever reaches the network.

`mavlink_transport.py` is this bridge's first real transport: `MavlinkFlightControl.send()` maps each request to a real, numbered `MAV_CMD` from the authoritative common.xml spec - `ARM` -> `MAV_CMD_COMPONENT_ARM_DISARM` (400, arm, requires `confirm_arm=True`); `DISARM` -> the same command with `param1=0` and never forced (an autopilot refuses it in flight by itself; there is deliberately no kill); `TAKEOFF` -> `MAV_CMD_NAV_TAKEOFF` (22, `COMMAND_LONG`); `GOTO_WAYPOINT` -> `MAV_CMD_DO_REPOSITION` (192, the real immediate-GUIDED-mode command, not the mission-item `MAV_CMD_NAV_WAYPOINT`), sent as a `COMMAND_INT`; `HOVER_AND_CAPTURE` -> `MAV_CMD_NAV_LOITER_UNLIM` (17) then `MAV_CMD_IMAGE_START_CAPTURE` (2000, one image; `camera_component` addresses a camera that is not the autopilot); `RETURN_TO_LAUNCH` -> `MAV_CMD_NAV_RETURN_TO_LAUNCH` (20); `LAND` -> `MAV_CMD_NAV_LAND` (21). A rejected `UavDispatch` is never sent, except `RETURN_TO_LAUNCH`, `LAND` and `DISARM`, which are sent anyway (as the simulated vehicle does).

**Units and altitude reference.** Latitude and longitude are decimal degrees; a `GOTO_WAYPOINT` carries them as degrees x 1e7 integers. Its altitude is in metres and its reference is explicit: `altitude_frame="relative"` (the default; above the takeoff point, `MAV_FRAME_GLOBAL_RELATIVE_ALT_INT`) or `"amsl"` (above mean sea level, `MAV_FRAME_GLOBAL_INT`). A `COMMAND_LONG` has no frame, so the altitude of `TAKEOFF` is whatever the autopilot takes it to be (PX4 reads above mean sea level, ArduPilot relative to home): check it on the autopilot in use before a flight. The yaw of a reposition and of a loiter is NaN, which keeps the current heading.

**Flight envelope.** `send(..., envelope=FlightEnvelope(max_altitude_m, max_radius_m, home_lat, home_lon))` refuses a `TAKEOFF` above the ceiling and a `GOTO_WAYPOINT` above it or farther from home than the radius (it needs a relative altitude to compare). The numbers belong to the deployment - nothing here assumes a ceiling - and the envelope is optional: without one only the universal range checks apply. It is a check in the coordination layer, not a substitute for a geofence loaded in the autopilot. `send(..., require_envelope=True)` refuses a `TAKEOFF` or a `GOTO_WAYPOINT` that comes without one, and `MissionUploader.upload_geofence()` loads the radius into the autopilot as a circular inclusion fence (MAVLink fence protocol) when `envelope.upload_geofence` is on (off by default).

**Flight policy of the job entry.** The command line builds `FlightPolicy` from `config/uav.json` (sections `envelope`, `confirmation` and `phases`). By default a request to arm, take off, go to a point or hover is refused unless (1) a flight envelope is configured (home point plus a ceiling of 30 m and a radius of 100 m, both editable) and the altitude and position the job names are inside it, and (2) the job carries `operator_confirmation`, a short token signed by the server with HS256 for that request and that `job_id`, valid once (`human_confirmation.py`). Coming home, landing and disarming never need either. With `phases.chain_in_flight` on (off by default) a go-to or a hover is also accepted with the vehicle in the air when the previous request of the flight was accepted and sent, no request to come home came after it, the gap is within `phases.chain_max_gap_s`, and the envelope and the confirmation are in force; arming and taking off always start from the ground. Simulator and emulator evidence only.

**Acknowledgements.** The link is shared with a ground station and cameras. After sending, the transport reads `COMMAND_ACK` until the deadline, skipping the acknowledgements of other commands and, when the message carries its source, of other systems; `MAV_RESULT_IN_PROGRESS` keeps it waiting for the final one. `open_mavlink_connection()` gives up with a clear error when no heartbeat arrives within `heartbeat_timeout_seconds` and returns an object that carries the `target_system` / `target_component` the heartbeat came from. Retrying a command with an incremented `confirmation` is not implemented. `open_mavlink_connection()` is the one place `pymavlink` (optional `[mavlink]` extra) is imported, lazily.

`takeoff_altitude_m`/`waypoint_lat`/`waypoint_lon`/`waypoint_alt_m` are validated before ever reaching the autopilot - non-finite (`NaN`/`+-inf`) values are always refused, latitude/longitude are checked against the real, universal +/-90/+/-180 geographic range, and altitude must be a finite, positive number. A maximum operating altitude is deliberately NOT a built-in number - that is a real, jurisdiction/deployment-specific parameter (e.g. FAA Part 107's own ceiling for small UAS), not a universal physical constant; a deployment supplies it through the `FlightEnvelope` above.

## The heartbeat watchdog is not optional

`HeartbeatMonitor` (`heartbeat.py`) is this project's own required safety piece, not an afterthought: a UAV bridge that cannot tell "recently confirmed reachable" from "silently gone" is unsafe by construction. It is explicit-`now`-driven (never reads a real clock internally), reports `LOST` from the very first check if no heartbeat was ever observed, and treats exactly-at-the-timeout as still `OK` (only genuinely exceeding it trips the failsafe) - see `tests/test_heartbeat.py` for the full, deterministic boundary suite. Its `failsafe_action` (default `RETURN_TO_LAUNCH`, or `LAND`; anything the transport cannot send is refused when the monitor is built) is a real signal for THIS bridge's own coordination layer - it is not, and must never be presented as, a replacement for the flight controller's own independent, firmware-level link-loss failsafe.

## Signing the MAVLink link

MAVLink 2 can sign every message with a shared 32-byte key, so that the vehicle accepts commands only from a station that holds the key and the bridge accepts telemetry only from a vehicle that does. `run --signing-key-file FILE` (or the file named by `HYDRA_UMC_BRIDGE_UAV_SIGNING_KEY_FILE`) turns it on: the file holds the key as 32 raw bytes or 64 hexadecimal characters, and it is never printed or put in a log. With a key, the bridge signs what it sends and refuses what is received unsigned; `--signing-allow-unsigned` keeps accepting unsigned messages for a vehicle that does not sign yet. The same key has to be set in the autopilot, following the documentation of its firmware. Signing authenticates the link, it does not encrypt it, and it is off unless a key is given. The same two options can be set by an administrator from the Server Admin screen of the control app: the Server saves them in the `mavlink` section of its `data/server-config.json` (`signingKeyFile`, the path of the key file and never the key, and `signingAllowUnsigned`), and `run --server-config FILE` (or the file named by `HYDRA_UMC_BRIDGE_UAV_SERVER_CONFIG`) reads that section when the bridge starts, so a change applies the next time the bridge is started. The order is always: the option of the command line, then the environment (`HYDRA_UMC_BRIDGE_UAV_SIGNING_KEY_FILE`, and `HYDRA_UMC_BRIDGE_UAV_SIGNING_ALLOW_UNSIGNED=1` to accept unsigned messages), then the Server configuration, then the default (no signing; unsigned messages refused when there is a key). A configuration file that is named but cannot be read, or whose `mavlink` section is malformed, stops the bridge with an error instead of starting without signing. It has been tested against a recorder of the pymavlink calls only, not against a vehicle or the simulator.

## Compatible platforms

The flight-request boundary is for UAV platforms reachable through a documented high-level interface: a Pixhawk/PX4-class flight controller over MAVLink (real, implemented above), or a DJI OSDK/Mobile SDK-class vendor interface (still future work, introduced only after that SDK is selected and tested). Sending a real command still requires a real MAVLink link (SITL, telemetry radio, or companion computer) and a real vehicle/simulator on the other end - this repository has not been exercised against either yet. The test emulator (`tests/mavlink_emulator.py`) is hand-written and checks the shape of what is sent (a reposition only as a `COMMAND_INT` with a known frame, ACKs, a pre-arm gate); it does not model the quirks of PX4 or ArduPilot, so a pass there is not a pass on a vehicle.

## Scripts and verification

| Script | Purpose | Changes version/CHANGELOG? |
|---|---|---|
| `build-test.bat` / `build-test.sh` | Compile Python and run local tests | No |
| `build.bat` / `build.sh` | Run the same validation, then build (never changes the version) | No |

Set `HYDRA_UMC_SDK_ROOT` when the SDK is not a sibling checkout. Use `build-test` during development; it is the only safe default before a real MAVLink/OSDK adapter exists.

## Adding a new script

Keep a new script in the repository root only when it is an operator entry point. Add the standard copyright header, state whether it mutates version/CHANGELOG, print numbered steps, and end `.bat` scripts with `pause`. Put reusable Python logic under `tools/`, compile it in `tools/build_test.py`, add deterministic tests for every new state mapping or failsafe transition, and document the command in the README and this guide. A script must not open a real transport, arm a UAV or send a flight command implicitly.

## Hardware acceptance gate

Before deploying an adapter: select the real flight controller/SDK and its authentication, document every flight request's real MAVLink message or OSDK call, bind authenticated UAV identity, verify the transport adapter genuinely calls `HeartbeatMonitor.observe()` on every real telemetry packet (not a fixed timer), independently confirm the flight controller's own RTL/Hover failsafe actually fires on a real link cut, and perform a tethered/geofenced bench test before any free flight. The flight controller's own firmware remains responsible for real-time stabilization and its own independent failsafe.

## The link monitor and the simulator check

`hydra-umc-bridge-uav run --connection URL --link-monitor` wraps the link in a `LinkedSink`: one thread (`MavlinkLink`) reads every message, the vehicle's `HEARTBEAT` refreshes the `HeartbeatMonitor` and the rest is kept by type for `recv_match`, which is what `MavlinkFlightControl` waits on for a `COMMAND_ACK`. Sending is passed to the underlying sink. Each status line then has a `link` object (`status` `OK` or `LOST`, `seconds_since_heartbeat`, `failsafe_action`, `reader_running`, `reader_error`). A link that cannot be read ends the thread and the monitor stops being refreshed, so it goes `LOST`; it never reports a link it can no longer read. This is the bridge's own signal and does not replace the failsafe of the autopilot.

`tools/sitl_smoke.py --connection udpin:0.0.0.0:14540` (the onboard link of PX4 SITL) runs that against a simulator that is already up and passes when its heartbeat was heard and the bridge sent its own. `.github/workflows/sitl.yml` (Actions, Run workflow) starts a PX4 SITL container and runs it; it pulls a large image, so it is never part of the normal checks; it passed against PX4 SITL 1.14.3 in Actions (the link stayed OK and the bridge sent its heartbeat), which says nothing about a real autopilot.

**Switches from Server Admin.** With `HYDRA_UMC_BRIDGE_UAV_REMOTE_SETTINGS=1` and the server configuration file named (`--server-config` or `HYDRA_UMC_BRIDGE_UAV_SERVER_CONFIG`), `bridges.uav.envelopeRequired` and `bridges.uav.confirmationRequired` can require the flight envelope and the human confirmation, and `bridges.uav.chainInFlight` and `bridges.uav.uploadGeofence` can switch chaining in flight and the geofence upload off. They only tighten: a value that would relax the host's own `config/uav.json` is ignored, and a damaged file takes the stricter side of every policy.
